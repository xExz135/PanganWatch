# Decisions

One line per decision and why. Each role edits only its own section (TEAM.md §2).

## Data Engineer

- **2026-10-25 — Geo-block test passed: PIHPS answers GitHub-hosted (US) runners.** No laptop/VPS fallback needed for ingestion.
- **2026-10-25 — Scrape per city, not per province.** PIHPS averages multi-area selections into one row, so per-city requests are the only way to compute our own province median (spec §6).
- **2026-10-25 — Backfill in calendar-year chunks, not months.** One year per request works (~40 s); 12× fewer requests than monthly chunks for the same data.
- **2026-10-25 — Bronze = raw files + append-only `_manifest.jsonl`, not a DuckDB table.** DuckDB allows one writer; a multi-day backfill writing to the DB would block `dbt build`. dbt reads the files directly (`bronze_pihps_raw` view), so bronze stays queryable and untouched.
- **2026-10-25 — Keep all 21 PIHPS commodities in bronze and silver.** Every request returns all of them at no extra cost; `is_v1` marks the spec's 8. Avoids re-scraping when rice premium, beef and sugar are added.
- **2026-10-25 — `province_id` = BPS province code.** Standard code that BPS CPI and weather sources also use; PIHPS's own id kept as `pihps_province_id`.
- **2026-10-25 — v1 rice = "Beras Kualitas Medium I", v1 oil = "Minyak Goreng Curah".** Spec says "beras (medium)" and "minyak goreng"; PIHPS has two medium grades and three oil types. Medium I is the reference grade; bulk oil moved most in the 2022 crisis and is what kitchens buy in volume.
- **2026-10-25 — Calendar-day look-backs for 7d/28d changes.** PIHPS skips weekends and holidays, so "7 days ago" means the latest price on or before date−7, NULL if stale.
- **2026-10-25 — Freshness test counts publishing days, not calendar days.** A calendar-day rule would fail every long weekend and the whole Lebaran break.
- **2026-10-25 — dbt generic tests written in-house instead of dbt-expectations.** Six small tests in `dbt/tests/generic/`; avoids a package download in CI for little gain.
- **2026-10-25 — pip + venv for now, not uv/Poetry.** uv isn't installed on the dev machine; `pyproject.toml` works with either.
- **2026-10-25 — CPI at three levels (national, province, city), food groups only.** National gives one unbroken 2021→now series across the 2024 base change; province matches the modelling grain; city is kept because it comes in the same requests.
- **2026-10-25 — Weather from Open-Meteo, not BMKG.** One free request returns 10+ years per province; BMKG's climate data needs an account and per-station work. One point per province (the capital) is a known simplification.
- **2026-10-25 — Weather history from 2015.** Rain anomalies need a "normal" to compare against; 10 years is enough.
- **2026-10-25 — USD/IDR from ECB via Frankfurter.** Official reference rate, free JSON API; JISDOR has no API and yfinance is unofficial.
- **2026-10-25 — Secrets never in URLs that get logged.** httpx's INFO URL logging is off; errors and manifests are redacted; tested.
- **2026-10-25 — `fct_pipeline_runs` / `fct_test_results` written by Python after `dbt build`, not by dbt.** A failed build must still be logged, and dbt can't log its own failure.
- **2026-10-25 — Daily job on GitHub-hosted runners, data kept in the `data` Release (owner decision).** Each run restores, runs, uploads. Raw data is stored as one archive per fetch month, so a run re-uploads only the current month. Raw archives are saved even when a run fails; the database is published only when every error-level test passes. Free, and git history stays small. Not MotherDuck: no extra account. Not the laptop: it would have to be on daily.
- **2026-10-25 — Run log kept as JSONL beside bronze, tables rebuilt from it.** A failed run never publishes the database, so a log stored only in the DB would lose failures; the JSONL travels with the raw archives.
- **2026-10-25 — Schedule off until `PIPELINE_ENABLED=true`.** If the scheduled job ran before the local backfill was uploaded, it would publish a month archive that the backfill upload would then overwrite.
- **2026-10-25 — Architecture diagram as Mermaid in the README, not `docs/architecture.png`.** GitHub renders it, it is diffable and can't drift from a binary copy. A PNG can be exported from it for the write-up if needed.
- **2026-10-25 — Missing sources give empty bronze views, not errors.** A fresh checkout without a BPS key still builds; tested.
- **2026-10-25 — Staging rebuilds fully from bronze each run (for now).** Simple and always correct; fine at today's ~2,000 files. Switch `stg_pihps_price` to incremental when the build passes ~5 minutes.
- **2026-10-26 — `tier_order` test checks national monthly medians with a 10% tolerance (owner-approved).** The first version (more than 5% of a commodity-month's days out of order) warned on 1,143 of 1,218 months: in real PIHPS data producer > wholesale on 24% of same-city days, and province monthly medians still break 29% of the time. National monthly medians break by more than 10% in 11 months (chili and shallot spikes, 2-province garlic), while swapping producer and retail flags 812. Still a warning. Tolerance: `tier_order_tolerance` in `dbt_project.yml`.
- **2026-10-26 — `statsmodels` as the optional group `.[analytics]` (owner-approved).** Only CI and the weekly workflow (which runs `analytics.run`) install it; the daily job stays light.

## Data Analyst

- **2026-10-25 — Money shown as `Rp 45,000` (English separators).** The UI is English and percentages use a decimal point; `Rp 45.000` next to `+12.3%` invites misreading. Spec allows either if consistent; formatting lives only in `dashboard/common.py`.
- **2026-10-25 — Dashboard pages in `dashboard/views/`, not `dashboard/pages/`.** A `pages/` folder triggers Streamlit's automatic navigation, which overrode `st.navigation` (wrong titles, layout ignored).
- **2026-10-25 — Page 1 watch list uses the spec's model-free alert rules until Phase 4.** High = 7-day change > 20 %; Watch = > 2 SD above the 28-day mean (spec §12). Model spike risk replaces it once `fct_spike_risk` exists.
- **2026-10-25 — Province map uses one dot per province (at its capital), not a filled choropleth.** No province boundary file is in the repo yet, and the dots keep the same diverging color story. Swap to a choropleth if a licensed GeoJSON is added.
- **2026-10-25 — Price up = red on cards (`delta_color="inverse"`).** The audience is a buyer: a rise is bad news.
- **2026-10-25 — Colors from the dataviz reference palette, validated.** 4 tier colors pass colorblind and normal-vision separation in light and dark; light-mode contrast is low for two, so every line is direct-labeled and every chart has a table view. Dark mode has its own sequential direction (low end recedes into the dark surface).
- **2026-10-25 — Persona split of "chili 8 kg/day" into 3 kg rawit + 5 kg keriting.** The spec gives one chili figure but models two chilies; the split is an assumption in `config/persona.yaml`.
- **2026-10-25 — Reference prices only from a traceable source, one per row.** Each row in `reference_prices.csv` names its regulation and links the official text, or a news report when no official copy is online (flagged `press_report`). Where nothing could be verified there is no row, so no compliance is computed: shallots before 20 Dec 2022, chili before 20 Dec 2022 (no reference existed), garlic before 26 Sep 2024 (first reference), bulk oil before 1 Feb 2022.
- **2026-10-25 — Bulk cooking oil has no ceiling after 12 Aug 2024.** Permendag 18/2024 sets the HET for Minyakita only; PIHPS's bulk oil (`curah`) is not Minyakita, so comparing it to 15,700 would be wrong.
- **2026-10-25 — A HAP range is compared on its upper bound.** Chili and shallot references are ranges (e.g. bird's-eye chili 40,000–57,000); "above the reference" means above the top. The lower bound is kept as `price_idr_low`.
- **2026-10-25 — Compliance uses the traditional and modern retail tiers.** Consumer references apply to retail sales; producer and wholesale prices are left out.
- **2026-10-25 — Streaks count published days.** PIHPS skips weekends and holidays, so `consecutive_days_above` counts days with a price, and a weekend does not break a streak.
- **2026-10-25 — Region-to-province map lives in `dim_reference_price`, not a second seed.** Regulations name regions ("Jawa, Lampung dan Sumatera Selatan"); the map follows their wording and is documented in the model's `.yml`. Rice zones changed in 2025 (Sulawesi moved to zone 2), so the seed lists regions per regulation rather than fixed zone numbers.
- **2026-10-26 — A5 uses the national price, detrended by a centered 365-day median, and reports the median year with the min–max range.** The centered window keeps slow inflation out of the Lebaran effect (fine for a look-back analysis; never used for forecasting). The median, not the mean, so one extreme year (2022 oil crisis, 2026 chili) doesn't set the headline; the range shows how much years differ. Base = the average of days −63 to −57, because PIHPS skips weekends and a single day −60 is often missing.
- **2026-10-26 — A national price needs at least 80% of the usual provinces that day.** On holidays one or two provinces report alone and their median is not a national price (MS-20261026-da-1). `ana_national_price` applies the rule for the analyses; the Today and Explore pages apply it in their own queries.
- **2026-10-26 — A6 jump risk = share of days followed by a 15%+ rise within 14 days.** The same definition as the forecasting team's spike label, so the dashboard's risk ranking and the spike model talk about the same event. Province series with one reporting city are flagged and left out of rankings; series with under 60 measurable days are dropped.
- **2026-10-26 — A1 shares are medians of same-day, same-province ratios, summarised per national month.** Ratios keep each comparison like-for-like (the same province on the same day); single days and provinces are too noisy (docs/source_notes.md). Commodities with producer prices from fewer than 10 provinces in a typical month are left out of the chart.
- **2026-10-26 — A2 runs on months, not weeks (spec deviation, owner_requests DA #5).** PIHPS updates producer prices about once a month (docs/source_notes.md), so a weekly regression measures the update calendar. Retail = the month's average; producer = the figure in force at month end; lags 0–2 months; pooled over provinces with province-clustered errors; the current incomplete month is left out. Besides the spec's test on total pass-through, a second test compares the same-month effects (speed).
- **2026-10-26 — A4 reports per regulation period and cites each regulation's source.** A streak counts published days above the reference and carries across a regulation change while the price stays above the new reference (as in `fct_reference_compliance`).
- **2026-10-26 — A3 times a link only where it is clear (best correlation ≥ 0.2).** With ~1,000 days, noise over 22 lags rarely exceeds 0.1, so the highest of 22 weak correlations would give a random lag. Rice shows almost no daily link, so its lags are not reported. Calendar-day lags; changes are between consecutive published days.

## Data Scientist

- **2026-10-25 — A forecast made on `run_date` uses only rows dated before `run_date`; `target_date = run_date + horizon_days` (calendar days).** Matches the leakage-guard wording ("every feature date < run_date"). A forecast is scored only if PIHPS published a non-imputed price on its target date; weekend and holiday targets stay unscored rather than being filled.
- **2026-10-25 — Backtest: one model per 4-week fold, forecasts issued every calendar day inside the fold.** Each model is trained on data before the cutoff and then forecasts daily with the newest history, like production (weekly retrain, daily forecasts). One forecast per fold would give only 13 points per series and horizon.
- **2026-10-25 — Seasonal naive uses a 7-day season.** A yearly season doesn't line up: Lebaran moves about 11 days earlier every year. The year-ago lag goes into the features instead. The season length is in `ml/settings.yaml`.
- **2026-10-25 — MASE scale = in-sample seasonal-naive MAE per series and fold, from observed pairs only.** Weekday gaps are skipped, not filled; a series that never moved gets no scale and is left out of MASE rather than giving infinity.
- **2026-10-25 — Baselines get honest 80% ranges too.** Their q10/q90 come from how far the same copy rule missed on the training data (log-ratio quantiles per commodity and horizon); q50 stays the copied price. Otherwise coverage could not be compared with the model's.
- **2026-10-25 — `pinball` in `fct_model_metrics` = mean pinball loss over q10, q50 and q90.** The contract has one pinball metric, not one per quantile.
- **2026-10-25 — Segment `ramadan_lebaran` = target date in Ramadan or up to 7 days after Lebaran** (from `dim_date`). Days before Ramadan stay `normal`; the window length is in `ml/settings.yaml`.
- **2026-10-25 — Leakage check = scramble, then remove, every row dated ≥ run_date; the output must not change.** Catches centered windows, negative shifts, full-sample statistics and row counts (all tested). Every feature function will go through it.
- **2026-10-25 — `ml` is not an installed package.** `tests/ml/conftest.py` puts the repo root on the path, and entry points run as `python -m ml.…` from the repo root, so no change to the DE-owned `pyproject.toml` is needed.
- **2026-10-25 — Gate 3 judged against naive with per-series ratios (owner decision).** MASE divides by the typical 7-day move in the training years, so it drifts above 1 at longer horizons and with the calmness of the test year, whatever the model's quality. The gate compares each model with naive on the same forecasts: MAE ratio per series, geometric mean across series (so beef doesn't outweigh rice), plus the share of series won. Seasonal naive lost to naive on every series in the first backtest, so it is reported but is not the bar.
- **2026-10-25 — `relrmse_naive` reported, not gated (owner decision).** Same per-series ratio as `relmae_naive` but with RMSE, which weighs big misses more; at 14 days 94% of naive's squared error is chili. It shows whether a model's gains come with worse spike misses. Theil's U2 measures the same thing (its denominator is the no-change forecast), so it is not added separately; RMSSE is not used because, like MASE, it scales by the training years' moves.
- **2026-10-26 — Live loop starts with the naive baseline, before the model exists.** A track record needs calendar time; publishing naive forecasts and scoring them daily now means the ledger has months of live history when a model passes Gate 3 and replaces it (`live.model` in `ml/settings.yaml`). Naive's live numbers also become the bar the model must beat live, not only in the backtest.
- **2026-10-26 — Forecast and ledger tables are written by Python, checked by dbt.** `ml.forecast` and `ml.ledger` append to `fct_forecast` / `fct_forecast_ledger` in the shared DB; dbt never rebuilds them, and the daily workflow restores and publishes the whole file. `dbt/models/ml/` holds views over them with error-severity tests (target date, q10 ≤ q50 ≤ q90, nothing written after its run date, ledger errors match). The views return no rows until the tables exist, so the first run cannot fail on them.
- **2026-10-26 — No backdated forecasts.** `ml.forecast --date` in the past writes nothing; a re-run on the same day writes nothing if that day is already published. A missed day stays missing.
- **2026-10-26 — The ledger scores a target once, after its day is over, on a non-imputed price.** Weekend and holiday targets are never scored; a late price is picked up on a later run; a scored row is never rescored, even if PIHPS revises the price later.
- **2026-10-26 — Forecast prices are whole rupiah; the range is widened to contain q50 after rounding.** For stable commodities the 1-day range is often a single price (q10 = q50 = q90): most days the price does not change, which the backtest's 84–87% coverage confirms.
- **2026-10-26 — LightGBM without mlforecast; ETS from statsmodels (owner decision).** mlforecast and statsforecast pin pandas < 3. Features come from `fct_features` in dbt anyway, and `ml.backtest` already handles origins, folds and leakage, so mlforecast would add little. Same method as the spec (global LightGBM, quantile objective, one model per horizon).
- **2026-10-26 — Features only use data that existed at the time, with each source's delay.** Prices up to the feature date; producer and wholesale at their last update (monthly / weekly); weather windows end 15 days earlier (the daily job revises the last 14 days, so newer values differ between training and serving); food CPI for month M from the 5th of M+1 (BPS releases early in M+1); FX up to the feature date. Calendar features of the target date are known in advance and allowed.
- **2026-10-26 — LightGBM target = log change from the last published price; weekend run dates are training examples too.** Each fct_features row serves the run dates up to the next published day (at most 3: Friday serves Saturday to Monday), with `gap_days_to_run` as an input, so training matches the daily job, which forecasts every calendar day. Calendar facts of the target date (Ramadan, days to Lebaran, holiday, weekday) are inputs; they are known in advance.
- **2026-10-26 — Each fold's 56-day validation slice is split: first half for early stopping, second half for the 80% range (conformalized quantile regression in log space).** Using one slice for both would make the range look better calibrated than it is. Quantiles are sorted after prediction so they never cross.
- **2026-10-26 — No tuning on the backtest's test windows.** Hyperparameters stay at the settings.yaml defaults for the first full backtest; any tuning will use validation slices only, otherwise the Gate 3 numbers would be optimistic.
- **2026-10-26 — First full LightGBM backtest misses Gate 3; the live model stays naive.** 13 folds (cutoffs 2025-10-28 to 2026-10). At 7 / 14 days: relMAE vs naive 0.991 / 0.997 (pass), series beating naive 40% / 42% (needs > 50%), 80% coverage 0.800 / 0.805 (pass); pooled MAE is 6–8% lower than naive. It wins on volatile commodities (shallots, chilies, chicken; 75–97% of provinces) and loses 1–5% on stable ones (rice, cooking oil, sugar, beef; 3–20% of provinces), where an unchanged price is hard to beat. Next step awaits the owner (per-commodity choice made on validation data, a gate change, or a better model for stable series).
- **2026-10-26 — `lgbm_routed`: LightGBM per commodity and horizon only where it beat naive on validation data (owner decision).** The choice uses the calibration half of each fold's validation slice (before the cutoff), comparing the median forecast's MAE with "same as the last price"; `routing.min_gain` = 0, fixed before the backtest ran. Routed series take the chosen model's whole forecast (median and range). Gate 3 is unchanged, so commodities that keep the baseline tie with naive and do not count as wins.
- **2026-10-27 — `lgbm_routed` backtest: better than LightGBM alone, still misses Gate 3; the live model stays naive.** At 7 / 14 days: relMAE vs naive 0.984 / 0.983 (pass), series beating naive 39% / 43% (needs > 50%; 50% / 48% counting ties), 80% coverage 0.830 / 0.822 (pass). Volatile commodities picked LightGBM 60–90% of the time and win in 65–97% of provinces; stable ones (rice, oil, sugar, beef) still switched to it 5–30% of the time on validation noise and lose slightly there. Raising `min_gain` now would be chosen after seeing test results, so it is not done; the proposed next step is a shadow run judged by the live ledger (awaits owner approval of LightGBM in the workflows).
- **2026-10-27 — Shadow run: `lgbm_routed` is published daily next to the live naive forecast (owner decision, LightGBM installed in the workflows with owner OK).** `ml.train` retrains it every Sunday on all published prices and saves `ml/models/lgbm_routed.json.gz` (boosters as text; version `lgbm_routed-<date>-<git>` inside, written as `model_version`); the weekly workflow uploads it to the `data` release and the daily workflow downloads it. `ml.forecast` publishes `live.model` first, then each `live.shadow` model, idempotent per model; a missing or failing shadow model is logged (and flagged as a warning on the Actions run) but never fails the daily job. The ledger scores both, so after ~4 weeks the two can be compared on data that did not exist when the model was built. Users keep seeing `live.model` only: dashboard pages must filter `fct_forecast` to it.
